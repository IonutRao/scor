# Scorul zilei (working name)

Motivational web app. People log good deeds (plus points) and less good ones (minus points), see a daily score, a streak and a journal. The owner is not a developer; Claude writes and ships all the code. Reply to the owner in plain language, without jargon, one step at a time: one short message, one thing for him to do, then wait.

## Layout

- `src/` is the source of truth: `app.css`, `logic.js` (pure scoring rules, also loaded by the node test), `i18n.js` (every UI string, Romanian and English, also loaded by a node test), `api.js` (the only file that talks to the network), `photo.js` (shrinks a chosen photo and keeps it on the device until it is uploaded), `camera.js` (the in-app camera: live picture in the page, a frame taken on tap), `app.js` (UI, routing, storage), `body.html`. `build.py` concatenates the scripts in the order `logic.js`, `i18n.js`, `api.js`, `photo.js`, `camera.js`, `app.js`.
- `build.py` assembles `src/` into the files GitHub Pages serves from the repo root (`index.html`, `sw.js`, `manifest.webmanifest`, icons) and into `artifact/scorul-zilei.html`, a preview page with example data that is not committed.
- Never edit the built files at the root by hand. Edit `src/`, run the build, commit sources and built files together.
- `test/logic.test.js` and `test/i18n.test.js` run under node. `test/flow.py` walks the built app with Playwright on a phone-size screen, including an offline start through the service worker.

## Commands

- Build: `python3 build.py`
- Tests: `TZ=Europe/Bucharest node test/logic.test.js`, `node test/i18n.test.js`, `python3 test/flow.py`, then the walkthroughs with accounts: `python3 test/accounts.py`, `python3 test/photos.py`, `python3 test/pulse.py`, `python3 test/edu.py`, `python3 test/old_server.py`. Each of those starts its own local database and test server on the same ports, so run them one after another, never together.
- The Playwright script launches `/opt/pw-browsers/chromium`. Google Fonts cannot load in the sandbox; the test ignores those failures only.

## Deploy

- GitHub Pages serves branch `main`, folder `/`, at https://ionutrao.github.io/scor/. Whatever reaches `main` is live within minutes.
- The version lives in two places that must change together: `VERSION` in `build.py` (names the service worker cache) and `VERSION` in `src/app.js` (shown in Profile).
- All paths are relative so the app works under `/scor/` and later under a custom domain.

## Product rules already decided with the owner

- An activity is worth 1 to 20 points, plus or minus. The score is per day.
- Streak: consecutive days that ended above zero. Today counts only once it is above zero, otherwise the streak runs through yesterday.
- Encouragements from other people are counted separately and never added to the score. On a public minus activity the button reads "Mâine mai bine" ("Trimis" once pressed; invitation "Spune-i tu primul") instead of "Încurajează" (0.6.2): the owner first wanted no button there; the argument that kept it is that admitting a slip in public is the honesty the app rewards, so it must not go unanswered while good deeds get cheers. It is the same cheer underneath, nothing changes in the database. The owner picked the wording after turning down "Susține", "Curaj" and "Respect".
- Visibility is per activity. Minus activities are private by default.
- An activity has a short title (up to 40 characters) and optional details (up to 300 characters, line breaks allowed). Details are never shown in lists: a small tag marks the activities that have them and the text appears on tap (the activity's dialog in Azi and Jurnal, an inline block in Flux). Whoever can see the activity can see its details. They can be written when logging, or added, changed and removed later; title and points still cannot be changed.
- An activity can have one photo. Photos need an account; the device-only mode does not offer them. The app shrinks the photo before upload (longest side 1280 px, JPEG, aiming under 350 KB), which also drops the place, camera and time stored inside the original. Like the details, a photo is never shown in lists: a small tag marks the activity and the picture appears on tap (the activity's dialog in Azi and Jurnal, under the title in Flux, where it is also only downloaded on tap). Whoever can see the activity can see its photo. It can be chosen when logging, or added, replaced and removed later on the "Detalii și poză" screen. On a touch screen the row offers two buttons, "Fă o poză" and "Alege o poză" (gallery or files); on a computer only the second (`TOUCH` in `src/app.js`, from `(pointer: coarse)` or `maxTouchPoints`).
- "Fă o poză" opens the camera inside the page (`src/camera.js`, `getUserMedia`, a frame drawn to a canvas on tap), not the phone's camera app: on the owner's Samsung the phone killed the page while its camera app was open (Chrome's "Unable to complete previous operation due to low memory"), so the photo and everything typed were lost. The frame is taken from the on-screen video, never through `ImageCapture.takePhoto()`, which on some phones comes back rotated. If the browser cannot start a camera (no `getUserMedia`, permission denied, no camera), the overlay says so and offers "Folosește camera telefonului", which opens the file chooser with `capture="environment"`, the phone's camera app; "Alege o poză" always opens the chooser without `capture`. The phone's Back button closes the camera (a history entry is pushed when it opens).
- What is typed in the activity form or on the details screen is saved as a draft (`scor.draft` in localStorage, with the chosen photo kept in IndexedDB) on every change and restored at start when the page reloads on the same `#plus`, `#minus` or `#detalii` route, for the same account, within 12 hours; a toast says "Am păstrat ce scriseseși". Leaving the form or saving clears it. This is what survives a reload forced by a low-memory phone.
- The save bar of the activity form is sticky, except while the details field is open (`.save-wrap.flat`). It used to switch back to sticky the moment the field lost focus, which could put it under the finger that had just tapped a button above it, and even press Save. Never tie it to focus again.
- Before the app is opened to strangers, public text and photos need a report button and a way for the owner to remove them. The owner knows; it is fine without them while he tests with friends.
- Romanian and English from the start. Every UI string lives in the `T` dictionary in `src/i18n.js`; both languages must have the same keys, and `test/i18n.test.js` checks it.
- Romanian text shown to people is written with diacritics, with ș and ț as comma-below letters (never the cedilla forms), and wording that agrees with the number next to it (1 încurajare, 2 încurajări). The owner's own chat preference (no diacritics, no hyphens) is about replies to him, not about the app.
- Default favorites and the activities logged from them are stored by key (`gym`, `smoke`) and named at display time, so their names follow the language and any later text correction. Since 0.6.3 a new account starts without "Țigară" and "Alcool" (the owner's call: they presume a habit and sit badly in the shared favorites of the educator mode); "Am amânat ceva" and "M-am enervat" took their place. The keys `smoke` and `alcohol` stay in the `fav` dictionary because older accounts still have them in their lists. Names people type are kept as typed; `fold()` in `src/app.js` compares names ignoring case and diacritics.
- Look: Manrope, one light theme, tokens at the top of `src/app.css`: indigo ink and score cards, mint for plus, coral for minus, gold for rewards.
- Kept deliberately small: no comments in the first versions, and no leaderboard by points. The owner asked for a "top 3 by points" and accepted the argument against it: points are self-reported, so a ranking rewards logging only the good deeds and hiding the rest, the opposite of the honesty the app is about. What replaced it is cooperative: the shared goal "Azi pe plus" (below) and the weekly line in Jurnal.
- Shared goal "Azi pe plus" (0.5): one card at the top of Flux, between the cheers card and the feed bar: "Azi pe plus", a count "3 din 5" (participants on plus out of participants), the first names of those on plus ("Ana, Bogdan și tu"), never who is not. Joining is opt-in with one tap ("Particip"), leaving with "Mă retrag"; the card tells non-participants what joining reveals: a single fact, whether their day is on plus. The day total behind it includes private activities; only its sign gets out, and only for participants. Non-participants still see the card (count and names), so they can be invited by it.
- Weekly line in Jurnal (0.5): under the chart, "5 din 7 zile pe plus · cea mai bună zi: marți, +25" (`weekLine()`); days before the first logged day are not counted, and on the first day it only says whether today is on plus.
- Agreed next steps, in this order: streak milestones (7, 30, 100 days on plus) with a small celebration in the app, a mark of honesty for days with minus items logged, then the final name, a domain and the report button before strangers come in. No new menus, no new screens.
- Educator mode (0.6, agreed with the owner on 2026-10-15): the checkbox "Țin scorul și pentru copii" in Profile turns it on. Children have no accounts; they are names in the educator's account (up to `KIDS_MAX` 12, names of 1 to 20 characters, unique ignoring case and diacritics). A small rounded button in the top corner of every screen shows who is selected ("Eu", "Maria") and opens a short list: Eu, each child, "Adaugă copil". The choice is remembered on the device (`data.who`) and shared by all screens; in Azi, Jurnal and the activity form it changes what is shown and whom the activity is logged for ("pentru Maria" under the title); in Flux and Profil it only shows the mode. Children's activities stay private: never in Flux, never counted in "Azi pe plus", no visibility row or button for them; the educator's own score, streak and cheers stay separate. Favorites are shared; any title can be typed. The button exists only while the mode is on. Removing a child deletes his activities (after a confirmation). The device-only mode has it too. The "Pentru cine?" list is also the overview (0.6.1): each row shows today's score and the streak on plus (`whoRow()`), in the order the children were added, never sorted by score: the owner asked for a children section sorted best first and accepted the argument against ranking children against each other (each child is compared with himself).

## Accounts and feed (version 0.2)

- Backend is Supabase, project URL in `src/config.json`. With URL and publishable key filled in, the build runs with accounts; with either one empty it stays in the device-only mode of 0.1. The preview artifact always stays device-only.
- `supabase/schema.sql` is the whole database: tables, grants, row level security, triggers and the functions the app calls (`me`, `set_name`, `sync`, `feed`, `cheer`, `pulse`, `delete_my_account`; `note_text` is a helper). It is idempotent and also upgrades a database created by an older copy of itself; the owner pastes it into the Supabase SQL Editor. The app talks to the database only through those functions.
- The owner runs the script by hand, so the app and the database are never updated at the same moment. Every release must hold in both directions: the new app on the previous script (what depends on the new script stays hidden) and the previous app on the new script. `sync` returns the script version as `v` (3 since details, 4 since photos, 5 since the shared goal, 6 since the educator mode); the app keeps it in `data.sv`, and `notesOn()`, `photosOn()`, `pulseOn()` and `eduAvail()` gate the details, the photos, the "Azi pe plus" card and the educator mode on it. A parameter added to a function gets a default, and the old signature is dropped in the script so there is never a second function with the same name. Publish the app first, then ask the owner to run the script.
- Details live in `entries.note`. `L.cleanNote()` in `src/logic.js` and `note_text()` in the script apply the same tidy-up rule; `test/accounts.py` compares them. New details travel inside `p_add`; later changes go through `data.outbox.note` and the `p_note` parameter, which is sent only when there is something in it.
- `src/api.js` is the only file that touches the network. It loads supabase-js from the CDN URL in `src/config.json`.
- On a device that has just signed in, the app does not know yet what the database can store. If that first answer arrives while the person is already typing an activity, `offerMore()` adds the details and photo rows in place instead of redrawing the form under their fingers.
- An answer that arrives after the person signed out, or signed in as someone else, is dropped: `sync()`, `pump()` and the account deletion compare `data.uid` and the `session` counter (bumped on every sign-out and on signing into another account) with the values they started with.
- Deleting an activity always queues the deletion for the account, even for an activity the account never confirmed: the confirmation may simply have been lost on the way, and the server ignores ids it does not know.
- The app is local-first: screens render from local data, `sync()` in `src/app.js` sends pending changes and pulls the account state in one call.
- `src/social.css` holds the styles for accounts, visibility and the feed; it is concatenated after `app.css`.
- The feed refreshes itself while the Flux screen is open and visible (`feedTick()` in `src/app.js`, every `FEED_EVERY`, 15 seconds; slower after failed attempts; nothing while the page is hidden or offline). It is plain polling of the `feed` function, not a live connection. `refreshFeed()` merges the newest page into what is on screen: no loading text, pages opened with "Mai multe" stay open, a reader who scrolled down keeps his place, and an encouragement the user just gave or withdrew is never overwritten by an older answer. Feed requests are numbered with `feedSeq`; an answer is used only if no other feed request started after it. The "Actualizează" link stays as a manual refresh. The feed shows only activities in the app's language (0.5.2 removed the "Toate limbile" toggle at the owner's request); switching the language in Profile reloads the feed.
- The user's own activities seen in the feed bring their encouragement counts with them (`noteMine()`); a full `sync` runs at most once a minute while Flux is open.
- New-in-feed dot (0.7): a small coral dot on the Flux tab when someone else posted something the person has not seen in Flux. `feedFresh` (runtime) is the newest other person's post known from any feed answer; `data.feedSeen` (persisted, per account) is set to it whenever Flux is on screen (`noteFresh()`, `markFeedSeen()`); `feedNew()` compares the two. While another screen is open and visible, `peekFeed()` asks `feed` for 5 rows every `PULSE_EVERY` (60 s; 4 s under `feedEvery=1000`), at once after sign-in and when the app comes back to the foreground. Own posts never light the dot; signing out, signing into another account or switching the language resets it. The owner asked for a silent push notification for every new post; agreed to start with this dot and leave real push notifications (Web Push, an Edge Function, VAPID keys, the app installed on the home screen) for after the domain, batched to at most one an hour. The peek is one more small request a minute per open app, fine for the test phase.
- Fine for the test phase, not for many users: every open feed asks for the newest page every 15 seconds and `sync` returns the whole journal each time. Before real scale, add a cheap "anything new" call or a live connection, and make `sync` send only what changed.
- Tests: `test/db/start.sh` starts a local PostgreSQL shaped like a Supabase project and loads the schema; `psql -h 127.0.0.1 -p 54329 -U postgres -d postgres -f test/db/security.sql` checks the access rules (also run with `SCOR_STRICT=1`); `python3 test/accounts.py` walks the app with several users against `test/server.py`, a stand-in for Supabase that uses `test/fake-supabase.js` in place of supabase-js. It takes about a minute and a half.
- `test/server.py` answers `/__test/set?feed=1000`: pages opened afterwards refresh the feed every second (`feedEvery` in the injected config) so the automatic refresh can be tested without waiting 15 seconds each time. The published build never sets `feedEvery`.
- Tests for the hand-run script: `python3 test/old_server.py` walks the current app on a database still on the previous script (`test/db/schema-0.5.sql`, loaded with `SCOR_SCHEMA_FILE`); `test/db/upgrade.sql`, run on such a database, loads the current script over existing data and checks nothing is lost. For the other direction, export the previous release (`git archive <commit>`), copy the current `supabase/schema.sql` and `test/db/setup.sql` into it and run its own `test/accounts.py`. When the script changes again, replace the snapshot with the script of the release being left behind.
- The sandbox cannot reach Supabase, npm or CDNs, so the real supabase-js and the real project are never exercised here. The first run against the real project has to be checked by the owner on the live site.

### Photos (version 0.4)

- The files live in Supabase Storage, in the private bucket `photos` (1 MB per file, JPEG only). `supabase/schema.sql` creates it together with three rules on `storage.objects`: upload only into your own folder and only with a name of the expected shape, read your own files or the photo of a public activity, delete your own files. A file sits at `{user id}/{name}`; `entries.photo` holds just `{name}`, which looks like `{16 hex digits}-{width}x{height}.jpg`. The size in the name lets the app give the picture a box of the right shape before it arrives.
- The storage part of the script sits before the functions on purpose: the app offers photos only once `sync` reports `v` 4, so if the storage part fails, the old `sync` stays and the app goes on without photos. The script never alters `storage.objects` and never deletes rows from it; Supabase refuses both to the SQL Editor.
- A new photo travels in this order: `PHOTO.shrink()`; the activity is saved on the device with `photo` set, the picture goes to IndexedDB (`scor-poze`, stored as raw bytes) and its name into `data.uploads`; `pump()` in `src/app.js` uploads one file at a time; only then does `sync` tell the account (`data.outbox.photo`, parameter `p_photo`, left out when empty). The account therefore never points at a file that is not there: `sync` also checks that the file exists in the person's folder before linking it (a stale change repeated after its file was deleted is ignored), and `p_add` ignores any `photo` field. `photoOps()` decides which changes may travel, and `canSend()` keeps `sync` from being called in a loop while a photo still waits for its upload.
- Files that no activity uses any more are removed by the app through the Storage API (`data.outbox.gone`), and only after the account has been told (`pendingCount() === 0`) and with a fresh view of it (a `sync` in the last `FRESH` 20 seconds, otherwise one is made first); SQL cannot do it. A name still used by some activity is never removed, whatever the list says. `applySync()` also releases every photo this device knew about that the account no longer has: replaced or removed on another device, or left behind by an activity deleted elsewhere. That rule relies on `sync` returning the whole journal and is skipped when the answer comes from a script without photos.
- When an upload fails: a file the server will never take (413 too big, 415 wrong kind) is given up at once; everything else (no connection, server error, any other refusal, a request with no answer for `PUMP_PATIENCE`, three minutes) is retried for as long as it takes, with growing pauses, because a refusal may come from a passing problem with the session or from a database that is not ready; a picture that vanished from the device before it could leave is given up, but an error of the device's own database is retried, not taken for a lost picture. Giving up always keeps the activity, tells the person, and tells the account the activity has no photo. The last refusal from storage is shown in Profile under "Salvare în cont" (`photoErr`), so a screenshot from the owner says what went wrong.
- Deleting the account: the app first waits for an upload in flight, asks the database for its version, lists and removes everything in the user's folder (100 per request) and only then calls `delete_my_account`, retrying that call a few times once the files are gone. The whole chain stops if the person signs out meanwhile.
- The file field is a single hidden `<input type="file" id="pic-file">` in `body.html`, outside the screens, opened by the buttons with `data-act="pic-pick"`. Keep it there: when the phone returns from the camera or the gallery the screen is redrawn, and a field that is redrawn loses the file that was just chosen.
- Known gaps, acceptable while testing with friends: a photo uploaded at the very moment of signing out, and the photos of an activity or account deleted from an app older than 0.4 on a phone that never had 0.4, stay in storage with nothing pointing at them (nobody can read them, they only take space). Two devices changing the same activity's photo while one of them has a lost answer end with the older photo back (the newer file is removed), never with a pointer to a missing file. Nothing limits how many files one person uploads. Before real scale, add a periodic clean-up that runs with the service key, and a limit.
- The release was reviewed by a separate agent before publishing; its findings (lost answers replayed, deletions never confirmed, account deletion continuing under another user, device database errors mistaken for lost pictures) are what the checks in `test/photos.py` with "raspuns pierdut", "intrerupta de iesirea din cont" and "eroare trecatoare" guard.
- Tests: `python3 test/photos.py` walks the feature with several users and devices in about two minutes, choosing files the way a person does, through the file chooser; a context with `has_touch` stands in for a phone, where the camera button must appear. Chromium runs with `--use-fake-device-for-media-stream` and `--use-fake-ui-for-media-stream`, so the in-app camera gets a moving test picture and permission without a prompt; a denied camera and a browser without `getUserMedia` are simulated with `add_init_script`. `test/kit.py` holds the helpers it shares with `test/old_server.py`. `test/db/setup.sql` imitates the `storage` schema (tables, helper functions, the trigger that refuses direct deletes); `test/server.py` answers `/storage/v1/object/...`, checks every request against the rules with the user's role and keeps the file contents in memory. `/__test/set?patience=2000` makes pages opened afterwards give up on an unanswered storage request after two seconds.
- `test/fake-supabase.js` copies supabase-js where it matters here: a Blob is sent with the Blob's own type (the bucket takes only `image/jpeg`), a failed download comes back as an unknown error wrapping the server's response, and signing out does not cancel the access token already issued.

### Shared goal "Azi pe plus" (version 0.5)

- Participation is a row in `public.pulse` (user id, since). The table has no grants and no policies: it is read and written only through the function `pulse(p_day date, p_join boolean)`, which is `security definer` (like `delete_my_account`), because it sums the private activities of participants; it returns only `{day, in, total, up: [names], others: [names without the caller], you: bool, v}`. The client shows "tu" from `you`, never by comparing names: on the owner's phone the card showed his name instead of "tu" (0.5), because the name kept on the device can differ from the one in the account (`others`/`you` were added in 0.5.1; a script without them falls back to a name comparison without case and diacritics). `sync` now also returns `name`, so a name changed on another device reaches every device. `p_day` is the viewer's local day from the device; a day more than one day away from the server's today is replaced by today. `p_join` true joins, false leaves, null just looks.
- Client: `loadPulse(join)` in `src/app.js`; the last answer is kept in `data.pulse` (shown at once when Flux opens, but only if it is for today's date); refreshed when Flux opens, every `PULSE_EVERY` (four times the feed interval, 60 s in production, 4 s under `feedEvery=1000`) while Flux is open, on "Actualizează", and after a `sync` that sent or deleted activities. Answers are numbered (`pulseSeq`) and dropped after sign-out like everything else. The viewer's own name in `up` is shown as "tu", last.
- Tests: `python3 test/pulse.py` (two users, join, up and down, leave, stale day, the Jurnal line); `test/db/security.sql` checks the function and that the table cannot be touched directly; `test/db/upgrade.sql` from the 0.4 snapshot.

### Educator mode (version 0.6)

- Database: `entries.kid uuid` (null for the adult's own activities) with the constraint `entries_kid_private` (a kid entry is never public; `sync` forces `is_public` false on insert and `p_vis` skips kid entries); `settings.kids jsonb` holds `{"on": bool, "list": [{"id", "name"}]}` (constraint `settings_kids_ok`: an object under 16000 bytes). `sync` takes `p_kids` (default null, sent only when the list changed on the device) and returns `kid` per entry and `kids`; `feed` and `pulse` leave out `kid is not null`. Script version 6.
- Client: `data.edu` (`{on, list}`), `eduRev`/`eduSynced` (like favorites), `data.who` (the selected child's id or null, device-local, not synced). `eduAvail()` is true in the device-only mode or once `data.sv >= EDU_FROM` (6); `eduOn()` adds the checkbox. Kid entries logged before the script is run wait on the device: `canTravel(e)` keeps them out of `sync` until the server is at 6, and `canSend()` does not call `sync` for them alone. `scope()` picks the entries of the selected person; `isKidEntry(e)` keeps them out of Flux, cheers and the shared goal on the client too. `upgrade()` drops a `kid` that is not in the list and forces `pub` false on kid entries.
- UI: `whoPill()` in `head()` on every screen, dialog "Pentru cine?" via `openDialog({ list })` (`#dlg-l` in `body.html`), screen `#copil` (`viewKid()`, `submitKid()`), `eduSection()` in Profile with the list and "Scoate" per child (`askRemoveKid()`), `#for-kid` and `#kid-private` in the activity form instead of the visibility row. The draft keeps `add.kid`.
- Tests: `python3 test/edu.py` (two children, separate scores, Jurnal following the selection, nothing in the feed or the shared goal, a second device, removing a child, mode off and on); `test/db/security.sql` has a "modul educator" block; `test/db/upgrade.sql` runs from `test/db/schema-0.5.sql` (the 0.5.1 script); `test/old_server.py` runs the current app on that snapshot and checks that the mode stays hidden and `p_kids` never leaves the device.

## Conventions

- Plain JavaScript without a build step or framework, so the whole app is one self-contained `index.html`.
- User-provided text is always escaped with `esc()` before it goes into markup.
- Browser storage access is wrapped in try/catch; the app must render without it.
- `confirm()` and `alert()` are never used; confirmations go through the `<dialog>` in `body.html`.
